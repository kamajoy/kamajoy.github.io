# PRD 开发手册(AI 执行版)

用户只会提供:**模式 + 接口 + TRD + PRD(章节/功能点) + 范围**。其余由你按本手册执行。

## 0. 铁律(所有模式、所有阶段)

1. 飞书文档只用 **飞书 CLI skill** 读取;**不改飞书文档,不 commit/push**。
2. **先读后写**;未读过的文档/代码不下结论。
3. **不确定就问,不猜**;**一次只问一个**阻塞性问题(格式见 §3)。
4. **只改必要的,其他不动**;超出已确认清单的改动,先停下问。
5. 所有结论标注类型:**[事实]**(带来源)/**[推测]**/**[冲突]**/**[缺失]**。
6. 每次回复首行输出状态条:`【模式 | 阶段 | 待确认数】`,末行写明"下一步 + 需要用户做什么"。
7. 用户说"确认/继续/OK"才能跨过 🚪关卡;沉默或模糊回答不算确认。

## 1. 模式与流程

| 模式 | 触发 | 流程 |
|---|---|---|
| **全流程** | 实现 PRD 新功能 | P0 → P1 → P2 → P3🚪 → P4 → P5 → 汇报 |
| **检查** | 核对功能是否完整 | P0 → P5 → (有缺口→P3🚪→P4→P5) |
| **修Bug** | 给出现象/报错 | P0 → B1 → B2🚪 → B3 → B4 |
| **调整** | 需求规则变更 | P0 → C1 → C2🚪 → C3 → P5(仅受影响项) |

未标明模式时:你判断并在首条回复声明"按【xx】模式执行",用户可纠正。

## 2. 阶段步骤

### P0 准备(只读)
1. 用飞书 CLI 读 TRD、PRD(只读用户指定章节+必要上下文)。
2. 读接口现有实现:入口、service、DTO/常量、相关测试。
3. 输出 **已读清单**:`文档/章节 → 关键规则`、`代码 文件:行 → 现状`。

### P1 需求分析(只读)
1. 把 PRD 功能点拆成编号条目 **R1…Rn**:每条含 `规则 | 来源 | 现状(已实现/部分/未实现) | 类型`。
2. 单列:**[冲突]**(TRD/PRD/代码互相矛盾)、**[缺失]**(文档没写)、**[推测]**。
3. 明确 **范围外**(已实现、用户声明不做的)。

### P2 澄清循环(只读)
- 按重要性每次问 1 个阻塞问题,收到回答后更新 R 清单,再问下一个。
- **非阻塞疑问**不逐个问:合并为"假设清单"(`A1…`),在 P3 一次性让用户确认。
- 无阻塞问题 → 进入 P3。

**是否重新分析?** 只在以下情况回到 P1,且只重读**受影响的部分**:
| 触发 | 动作 |
|---|---|
| 回答改变了范围或规则 | 更新受影响 R 条目 |
| 回答推翻了某条 [事实]/[推测] | 重读相关文档/代码 |
| 发现 PRD 指定章节外还有关联规则 | 补读后更新 |
| 其他情况 | **不重做**,直接继续 |

### P3 方案 🚪
输出以下固定结构,等用户确认:
```
【需求复述】逐条 R1…Rn(规则+来源)
【范围外】
【假设清单】A1… (默认值,用户可否决)
【改动清单】文件路径 | 所属项目 | 改动要点 | 对应 R
【验证用例】正常 / 边界 / 异常 各至少 1 条,对应 R
【风险】
```
用户纠正 → 改后重新输出,不得直接编码。

### P4 编码
1. 严格按【改动清单】;新增/超出文件先问。
2. 每个改动可追溯到 R 编号。
3. 不提交 git,不改飞书。

### P5 完整性检查(只读)
逐条核对 R 清单 vs 代码,输出表:
| R | 需求 | 状态 ✅/⚠️/❌ | 证据(文件:行) | 备注 |
- 全 ✅ → 汇报。
- 有 ⚠️/❌ → 列缺口与最小修复方案,等确认后回 P4,修完再 P5(只复查缺口项)。

### 汇报(固定三段)
```
【改了什么】文件 + 要点(对应 R)
【没改什么】刻意未动的相关部分及原因
【怎么验证】请求示例 / 期望返回 / 边界用例 / 已跑的测试
```

### 修Bug 子流程
- **B1 定位(只读)**:复现路径 → 定位代码 → 给出**根因**,标明 [事实]/[推测];并对照 PRD/TRD 判断是 *代码偏离需求* 还是 *需求本身有歧义*(后者转问用户)。
- **B2 修复方案 🚪**:最小改动方案、影响范围、回归点。
- **B3 修复**:只改方案内文件。
- **B4 验证**:原现象 + 相邻场景回归,按汇报三段输出。

### 调整 子流程
- **C1 差异(只读)**:`旧规则 vs 新规则` 对照表 + 受影响的 R/代码位置 + 与 TRD/PRD 是否冲突。
- **C2 方案 🚪**:同 P3 结构,但只含变更项。
- **C3 修改**:只动受影响处。
- 然后对受影响 R 做 P5。

## 3. 提问格式(一次一个)
```
❓ 问题:(一句话)
为什么关键:(不确认会导致什么)
选项:A. … (建议) B. … C. 其他
```
给出推荐项,方便用户只回 "A"。

## 4. 用户快捷指令
`确认`/`继续` 过关卡 · `重新分析` 回 P1 · `跳过分析` 直接 P3 · `只检查` 进 P5 · `只读` 本轮禁止改文件 · `列清单` 重输出当前 R 清单/改动清单

## 5. 常见错误
- 阶段 P1~P3 就改文件 ❌　一次问多个问题 ❌　把推测写成事实 ❌
- 澄清后无脑重读全部文档 ❌(只读受影响部分)　跳过 P3 复述直接编码 ❌
- 修 Bug 时顺手重构 ❌　汇报缺"没改什么/怎么验证" ❌
