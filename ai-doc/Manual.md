# AI 协作速查手册

> 万能口诀：**先读后写、小步改、必验证、留记录**
> 典型一条龙：`梳理 → 方案 → 开发 → 验收 → 交接摘要 → 发布前检查`

**万能约束（可贴在任何任务前面）**

```
先读后写；不确定就问，不要猜；只改必要的，其他不动。
完成后说明：改了什么 / 没改什么 / 怎么验证。
```

# 一、理解类

## 1. 项目概要总结　口诀：一屏看懂

**目的**：接手/回顾项目，要一眼看懂，不要长文档。

```
请用【一屏能看完】的方式总结这个项目的实现，严格遵守：

1. 总字数不超过 300 字
2. 只写以下 4 部分，每部分最多 3 条，每条一句话：
   - 做什么：项目解决什么问题
   - 核心流程：用 "A → B → C → D" 的箭头链表示主逻辑
   - 关键模块：模块名 + 一句话职责（不超过 15 字）
   - 注意点：最容易出错或最关键的设计决策
3. 不要写背景、优点、使用说明，不要贴代码
4. 不确定的地方不要展开，直接标 "?"
```

**文档已经很长时，用压缩版**：

```
把上面的内容压缩到原来的 10%，只保留：
① 整体流程（一行箭头）② 3~5 个关键模块 ③ 1~2 个关键决策。其余全部删掉。
```

**限制词（按需追加）**：只说主干 / 假设我只有 30 秒读 / 像给同事口头交代 / 不要小标题。
**还是太长**：回一句"**太长了，砍一半。**"

**验收**：30 秒内能复述"做什么、怎么流转、哪里最容易错"。

---

## 2. 功能逻辑梳理　口诀：只看不改

**目的**：搞懂某个功能怎么跑的（比项目概要更聚焦）。

```
梳理【功能名】的实现逻辑。只读代码，不要修改任何文件。
输出（≤300 字）：
1. 入口 → 出口：箭头链，每步标 文件:函数名
2. 关键模块：模块 + 一句话职责
3. 数据：涉及的表/字段/接口
4. 坑点：最容易误改的 1~3 处
不确定的地方标 "?"，不要猜。
```

**验收**：能说出"请求从哪进、经过谁、落到哪"。

# 二、开发类

## 3. 技术方案设计　口诀：先比方案再选

**目的**：大需求/有多种实现路径时，先定方案再写代码。

```
需求：【描述】。先不要写代码，输出技术方案：
1. 现状：相关模块 + 可复用点（文件:函数）
2. 备选方案 2~3 个：各一句话 + 优缺点 + 改动量
3. 推荐方案及理由（≤3 条）
4. 风险与未决问题（需要我拍板的单独列出）
5. 拆成可独立验证的小步骤
等我选定后再动手。
```

**验收**：备选有对比；待拍板问题明确；步骤可拆分。

---

## 4. 新需求开发　口诀：先方案后动手

**目的**：加新功能，不破坏旧逻辑。

```
需求：【一句话描述】
请按步骤执行：
1. 先阅读相关代码，找出可复用的现有逻辑（不要重复造轮子）
2. 给出方案（≤200 字）：改哪些文件、新增什么、影响哪些现有功能 —— 等我确认再动手
3. 确认后小步实现，遵循项目现有风格
4. 补测试或写验证步骤
5. 完成后按「14. 交接摘要」写到 docs/changes/
```

**验收**：方案先过目 → 改动范围可控 → 有验证 → 有摘要。

---

## 5. 功能逻辑修改　口诀：先问影响面

**目的**：改已有行为（规则变了），最怕牵一发动全身。

```
把【功能名】的逻辑从【旧行为】改为【新行为】。
动手前先列出：
1. 当前逻辑所在位置（文件:函数）
2. 所有调用方 / 依赖方（用搜索确认，不要凭印象）
3. 可能受影响的功能和数据（含历史数据兼容）
等我确认后再改。改完说明：改了什么、没改什么、如何回滚。
```

**验收**：影响面清单齐全；旧场景回归通过；同步更新原功能的交接摘要。

---

## 6. 重构 / 升级迁移　口诀：行为不变，小步走

**目的**：整理代码结构、升级依赖/框架版本，不改变对外行为。

```
目标：【重构/升级什么，为什么】。硬性要求：
1. 对外行为不变（接口、数据、输出一致），不夹带新功能
2. 动手前确认有测试兜底；没有就先补"保持当前行为"的测试
3. 拆成小步，每步可单独提交、可回滚，每步后运行测试
4. 升级依赖：先读 changelog 的破坏性变更，列出受影响的用法再改
5. 结束时说明：改动范围、行为是否有差异、回滚方法
```

**验收**：测试前后全绿；diff 里没有功能变化。

---

## 7. 性能优化　口诀：先测量再动手

**目的**：解决"慢、卡、占资源"，避免凭感觉乱优化。

```
问题：【哪里慢/占资源，现状数据】　目标：【期望指标】
1. 先定位瓶颈，给出证据（耗时分布 / 慢查询 / profile），不要凭感觉
2. 列出候选优化点，按"收益/改动量"排序，我选定后再改
3. 一次只改一处，改前改后用同一方法测，贴对比数据
4. 说明代价（内存、复杂度、一致性风险）
```

**验收**：有前后对比数据；功能结果不变；代价已说明。

# 三、排错类

## 8. Bug 修复　口诀：先复现再改

**目的**：修问题，要根治，不要掩盖。

```
Bug：【现象】
预期：【应该怎样】　实际：【实际怎样】
线索：【报错/日志/触发步骤】
请按步骤执行：
1. 先复现（或写出能复现的测试），复现不了就告诉我，不要瞎改
2. 定位根因：说明"为什么会这样"，一句话
3. 最小改动修复，不顺手重构
4. 验证：原 bug 消失 + 相邻功能没坏
5. 用一句话总结：根因 / 修复点 / 验证方式
```

**验收**：能说清根因；改动最小；有回归验证。

---

## 9. 线上问题排查　口诀：先止血，再找根因

**目的**：生产出问题，先控制影响，再慢慢查（与 Bug 修复的区别：时间紧、不能乱试）。

```
线上现象：【描述】　影响范围：【用户/时间】　最近变更：【发版/配置/数据】
不要直接操作线上环境，只给方案和命令，由我执行。请按顺序：
1. 止血方案：回滚 / 开关 / 降级 / 限流，哪个最快最安全（先给这个）
2. 线索收集：要看哪些日志、监控、数据（给出具体查询语句）
3. 假设列表：按可能性排序，每条写"如何证伪"
4. 逐个验证后再给根因；证据不足就标 "?"，不要下结论
5. 根因确认后走「8. Bug 修复」；事后补 3 行复盘：原因 / 修复 / 预防
```

**验收**：先有止血动作；根因有证据；有复盘。

# 四、质量类

## 10. 补测试　口诀：测行为，不测实现

**目的**：给已有功能补单测/集成测试。

```
为【功能/函数】补测试。先读代码和现有测试风格。
1. 先列"行为清单"：正常路径 / 边界（空值、极端值）/ 异常路径 / 权限
2. 每条行为一个用例，命名写清"给定…当…则…"
3. 只测对外行为，不测内部实现细节；不为凑覆盖率写无意义用例
4. 运行并贴结果；抽 1~2 个用例，故意改坏代码确认它会失败
```

**验收**：行为清单被覆盖；故意改坏代码时用例会红。

---

## 11. 验收检查　口诀：逐条对照，要证据

**目的**：确认改动符合 PRD、Bug 真的修好、没改多。

> 建议**新开一个会话**让 AI 验收（写代码的 AI 容易"自己说自己对"）。把 PRD / Bug 描述 + `git diff` 一起给它。

```
你是验收人，不是开发者。只检查，不修改代码。
输入：PRD/需求/Bug 描述（见下）+ 本次 git diff
请按以下三步输出：

1. 需求对照表（把 PRD 拆成一条条）
| PRD 条目 | 对应实现（文件:函数） | 结论 ✅符合 / ⚠️部分 / ❌缺失 / ?无法确认 | 证据 |
- 每条结论必须有证据（代码位置或测试结果），没证据一律标"?"，不要默认通过

2. Bug 验证（如有）
- 原因是否被根治？还是只是掩盖现象？
- 原复现步骤现在的预期结果是什么？有没有对应测试？

3. 越界与风险
- diff 里有没有 PRD 之外的改动？
- 边界情况：空值 / 极端值 / 权限 / 历史数据 / 并发，各一句话
- 可能受影响的相邻功能

最后给结论：可合并 / 需修改（列出必改项，按严重程度排序）
```

**再补一刀（让 AI 真跑起来）**：

```
请实际运行相关测试 / 构建 / lint，贴出结果。
没有测试的话，写出 3 条手动验证步骤（操作 → 预期结果）。
```

**验收**：每条 PRD 都有 ✅ 且有证据；Bug 有对应验证；无越界改动。

### 11+. 改动在未上线分支时（精准圈定范围）

**核心**：别让 AI 自己"猜改了什么"，先用 git 把范围圈死，再喂给它。

```
git fetch origin
git log --oneline origin/main..feature/xxx          # 本分支独有的提交
git diff --stat origin/main...feature/xxx           # 改了哪些文件
git diff origin/main...feature/xxx                  # 完整改动
```

> 注意是**三个点 `...`**：只看分支自己的改动（从分叉点算起），不会混入 main 上别人的新提交。把 `feature/xxx` 换成你的分支，`main` 换成基线分支。

**提示词**：

```
请验收分支 feature/xxx 相对 origin/main 的改动。
范围限定：只看 `git diff origin/main...feature/xxx`，范围外的代码不评价。
步骤：
1. 运行上面三条 git 命令，先列出：提交列表、改动文件清单
2. 对每个改动文件，读分支上的完整文件（不要只看 diff 片段），理解上下文
3. 按"验收检查"的三步输出：需求对照表 / Bug 验证 / 越界与风险
4. 额外检查：
   - 分支是否落后 main？（`git rev-list --left-right --count origin/main...feature/xxx`）
   - 与 main 合并是否有冲突或逻辑冲突（别人改了同一块代码）
   - 分支里是否混入无关提交（调试代码、别的需求）
只检查，不修改代码。
PRD / Bug 描述如下：……
```

**常见情况**：

| 情况 | 做法 |
|---|---|
| 分支里有别人/别的需求的提交 | `git log` 找出本需求的提交，用 `git diff <首个提交>^..<末个提交>` 只看这段 |
| 只想验某一个 commit | `git show <commit>` |
| 想验证"功能真能跑" | 切到该分支（或 `git worktree add ../验收 feature/xxx`）再跑测试/手动步骤 |
| 分支落后 main 很多 | 先让 AI 判断是否需要 rebase/merge，再验收，避免验的是过期代码 |
| 有 PR | 直接给 PR 链接或 `gh pr diff <编号>`，范围最准 |

**一句话**：给 AI 的永远是 **"分支名 + 基线 + diff 命令 + PRD"**，四样齐了就不会查偏。

**小技巧**：
- PRD 太长时，先让 AI"把 PRD 拆成可检查的条目清单"，你确认后再逐条验。
- 你自己抽查 2~3 条"❌/?"以及最关键的 ✅，不用全看。
- 发现问题，把对照表里的 ❌ 条目直接贴回给开发 AI 修。

## 12. 代码评审　口诀：先看风险，再看风格

**目的**：评审别人（或 AI）提交的 PR/分支。与 11 的区别：11 对照需求，12 看代码质量与风险。

```
评审【PR/分支】的改动（范围：git diff origin/main...分支）。只评审，不改代码。
按严重程度分级输出：
🔴 必改：Bug、安全（注入/越权/敏感信息泄露）、数据丢失、并发问题
🟡 建议：可读性、重复代码、命名、缺少测试
🟢 可选：风格偏好
每条写：文件:行 + 问题 + 建议改法。
没发现问题的维度也写一句"已查，无问题"，不要为凑数硬挑毛病。
```

**验收**：🔴 项都有明确处理；每条意见可定位、可执行。

---

## 13. 发布前检查　口诀：能发、能验、能退

**目的**：上线前最后一道关，避免"代码没问题但发布出事"。

```
检查分支【xxx】的发布准备情况（只检查，不改代码）：
1. 数据：有库表/字段变更吗？迁移脚本可重复执行吗？兼容旧数据吗？
2. 配置：新增的配置项/环境变量/开关，各环境都配置了吗？
3. 兼容：接口是否向后兼容？前后端/多服务发布顺序有依赖吗？
4. 灰度：能否开关控制或灰度发布？
5. 回滚：出问题怎么退？代码回滚后数据还能用吗？
6. 观测：上线后看哪些指标/日志确认没问题？
输出：清单（✅/❌/?）+ 阻塞项。
```

**验收**：无 ❌ 阻塞项；回滚方案和观测点已写明。

# 五、沉淀类

## 14. 需求改动交接摘要　口诀：可定位、可验证

**目的**：做完需求/改动后，留一份给"下一个 AI/同事"的摘要。重点是文件路径、函数名、数据流、约束，不是讲故事。

```
请为本次改动写一份"交接摘要"，供其他 AI 快速接手。要求：

1. 先运行 `git diff --stat`，改动清单以实际 diff 为准，不要漏文件、不要编造
2. 严格按下方格式，总长不超过 400 字
3. 不要写背景、不要贴代码、不要解释"为什么这么做"（关键约定除外）
4. 保存到 docs/changes/YYYY-MM-功能名.md，并在 CLAUDE.md 的"功能索引"追加一行

格式：

# 功能：一句话描述

## 入口 → 出口
箭头链写主流程，每步标 文件:函数名

## 改动清单
| 文件 | 改了什么（一句话） |
只列实际修改/新增的文件。

## 未改动（防误改）
列出相关但没动的关键逻辑，没有写"无"

## 数据变化
新增/修改的表、字段、接口、配置项，没有写"无"

## 关键约定（别人改这里容易踩坑）
最多 3 条

## 怎么验证
1~2 条：测试文件路径或手动步骤
```

**验收**：别的 AI 只读这份摘要，就能定位到代码、知道哪些别乱动、知道怎么验证。

```markdown
## 功能索引

## 协作规则
1. 先读后写；不确定就问，不要猜；只改必要的，其他不动

   - 按"交接摘要"格式在 docs/changes/ 下新建 md（≤400 字，只写文件路径、函数名、数据变化、关键约定）
   - 在本文件"功能索引"追加一行
3. 修改已有功能时，同步更新对应摘要文件
4. 总结项目/功能时，≤300 字，用"箭头流程 + 关键模块"，不写背景和代码
5. 验收类任务只检查不修改，每条结论必须有证据
```

## 通用小技巧

- **分阶段确认**：方案、影响面这类"确认点"别省，改错再返工更贵。
- **AI 乱改时**：回一句"**只改必要的，其他不动**"。
- **说不清就停**：回一句"**不确定的先问我，不要猜**"。
- **改完必做**：`git diff --stat` 对照一遍，确认没改到无关文件。
- **长任务**：让 AI 先写计划，再逐步勾选执行。
- **验收换会话**：写代码和验收不要用同一个会话，避免自我确认。
- **技巧总结**:
```doc
1.@Superpowers 使用 brainstorming 梳理这个需求。一次只问我一个问题，方案确认前不要改代码。

2.执行过程中调整逻辑：
从现在开始改用这个规则：……已完成且正确的检查不要重复，继续处理剩余步骤。

3.方案功能完整性检查：
- 现在进入【方案功能完整性检查】阶段。
```
