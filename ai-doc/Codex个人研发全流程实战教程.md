# Codex 个人研发全流程实战教程

> 适用对象：已有开发环境和基础编码能力、刚开始使用 AI 研发工具的个人开发者  
> 主要环境：macOS、Codex 桌面客户端、VS Code、Codex CLI、Go、MySQL、HTTP/RPC、多代码仓库  
> 文档版本：2026-10-20  
> 配套文件：[快速操作清单](./Codex个人研发快速操作清单.md) · [提示词模板](./Codex个人研发提示词模板.md) · [HTML 手册](./Codex个人研发手册.html)

## 0. 先记住这四句话

1. **默认先确认需求与方案，再确认实施计划，之后才让 AI 改代码和测试。**
2. **最终产物主要是文档时用 ChatGPT Work，主要是代码时用 Codex。**
3. **让 AI 提供实际运行的命令与结果，不接受“应该没问题”。**
4. **本教程默认不 commit、不 push、不进行任何 PR 变更、不部署、不发布、不连接或写入任何数据库、不改变外部系统。**

本教程的“全流程”指本地需求分析、设计、实施、验证与交接。部署、数据库执行、真实环境联调与上线验收由人工完成；本地通过不等于生产验收通过。

如果时间很少，每次任务按下面三个阶段操作。一个阶段可以有多条消息，不是限定只聊三轮：

```text
第一阶段：只读分析需求和现有实现，先复述已读规则及来源；区分事实、推测、冲突和缺失，一次只问我一个关键问题，不修改文件。

第二阶段：先输出方案、影响范围、风险和非目标，等我确认；再输出实施与验证计划，再等我确认。草案只展示在对话中。

第三阶段（方案和计划均已批准后）：在约定文件范围内实施，先排除会连接数据库或外部系统的测试，再运行相关本地验证并 Review 最终差异。禁止 commit、push、任何 PR 变更、部署、发布、连接或写入数据库，以及改变外部系统。
```

## 1. 这套方法解决什么问题

你的主要工作可以归纳为六类：

| 工作 | 真正目标 | 常见风险 |
|---|---|---|
| PRD 梳理 | 把业务意图变成无歧义、可验收的需求 | AI 自行补规则、设计稿与文字冲突 |
| 方案讨论 | 找到满足需求且适合现有系统的实现方式 | 未读代码就设计、忽略兼容性 |
| 新功能 | 在既有工程中完成可验证的行为变化 | 改动扩散、缺少异常流程与测试 |
| Bug 修复 | 用证据定位根因并防止复发 | 根据报错猜修、用重试掩盖问题 |
| 重构 | 改善结构但保持业务行为不变 | 把重构变成改需求或大改接口 |
| 性能优化 | 在相同条件下获得可量化改善 | 没有基线、只凭代码观感优化 |

最佳协作方式不是一句“帮我完成”，而是明确设置四个关口：

```text
需求关口 -> 方案关口 -> 修改关口 -> 验收关口
```

- **需求关口**：目标、边界、非目标、验收条件是否明确。
- **方案关口**：是否基于真实代码和数据，而不是通用经验。
- **修改关口**：你明确确认后才允许编辑文件。
- **验收关口**：只有实际检查通过，才能说完成。

## 2. ChatGPT Work、Codex 和插件分别做什么

### 2.1 ChatGPT Work

适合以资料和决策为中心的任务：

- 阅读 PRD、飞书文档、Word、Excel、设计稿和历史方案；
- 对比多份资料，识别冲突和遗漏；
- 组织业务流程、边界、验收标准和待确认项；
- 讨论方案的业务取舍；
- 生成给 Codex 使用的“AI 执行版需求”。

**不要让 Work 仅凭 PRD 猜测真实项目结构。**涉及现有代码、依赖、测试命令和改动范围时，应切到对应仓库的 Codex 任务。

### 2.2 Codex

适合以真实工程和可执行验证为中心的任务：

- 阅读代码、配置、SQL、调用链和 Git 差异；
- 根据已确认 PRD 设计技术方案；
- 新增功能、修复 Bug、重构和性能优化；
- 运行 `gofmt`、`go vet`、`go test`、构建和本地验证；
- Review 未提交修改，报告风险和未验证项。

### 2.3 Superpowers

Superpowers 不是模型，也不是一个终端命令。它是一组研发工作流 Skills，重点约束 AI **先理解、再设计、再实现、最后验证**。

| Skill | 什么时候用 | 你会看到什么 |
|---|---|---|
| `brainstorming` | 新功能、复杂需求、架构调整 | AI 一次问一个问题，形成设计并等你确认 |
| `writing-plans` | 已确认的复杂多步骤方案 | 可执行的任务拆分、文件和验证步骤 |
| `test-driven-development` | 新行为或 Bug 修复 | 先失败测试，再最小实现，再回归 |
| `systematic-debugging` | Bug、测试失败、异常性能 | 复现、证据、根因、验证假设 |
| `verification-before-completion` | 准备宣布实现完成时 | 对本次实现执行相关验证；只做交接/整理时引用已有证据并标明范围与时间 |
| `requesting-code-review` | 功能完成、本地交付前 | 按严重度检查 Bug、回归和缺失测试 |
| `using-git-worktrees` | 确实需要隔离并行工作时 | 创建独立工作目录；本教程仍禁止 commit |

Superpowers 安装后通常会根据任务自动选择 Skill。你也可以在 Codex 中明确输入：

```text
@Superpowers 使用 brainstorming 梳理这个需求。一次只问我一个问题，方案确认前不要改代码。
```

如果客户端支持 Skill 选择，也可以从 Skills 列表选择对应 Skill。不同客户端的入口可能变化，**不要把 `@Superpowers` 当作 shell 命令执行**。

### 2.4 OpenSpec

OpenSpec 用于把长期、复杂或跨服务变更保存成项目内的规格、提案和任务记录。它不是所有任务的必需品。

| 情况 | 是否使用 OpenSpec |
|---|---|
| 单文件小修、小范围 Bug | 不用，Superpowers 足够 |
| 一般新功能，1 个仓库，需求已稳定 | 通常不用；先用 Superpowers |
| 跨多个服务或涉及公共接口/数据契约 | 建议使用 |
| 多阶段交付、多人协作、需要长期追踪规格 | 建议使用 |
| 需求仍很模糊 | 先用 `brainstorming`，不要急着建 OpenSpec 提案 |

- **Superpowers 管方法**：如何提问、设计、调试、测试和 Review。
- **OpenSpec 管持久化规格**：决定了什么、改什么、有哪些任务、完成到哪里。

## 3. 你的默认安全与执行边界

### 3.1 允许 AI 自主执行

- 阅读本地需求、代码、日志、配置示例和 Git 状态；
- 使用 `rg`、`git status`、`git diff` 阅读源文件与现有差异；
- 在方案与实施计划均获批准后编辑约定范围内的本地代码和测试；
- 运行不连接任何数据库或外部系统的格式化、静态检查、单元测试和本地构建；
- 在对话中生成 SQL、接口请求示例和操作步骤；保存为文件需有准确路径和文档写入授权，不执行数据库或外部写入；
- Review 本地差异并生成交付报告。

### 3.2 必须先问你

- 需求资料冲突，且不同选择会改变业务结果；
- 需要新增表、公共接口、依赖或改变兼容性；
- 需要修改范围外文件或做无关重构；
- 需要启动会长期运行的服务，或需要下载依赖、访问内网；
- 需要创建 Worktree、分支或改变 Git 工作区状态；
- 测试需要访问测试环境、真实数据或外部服务；
- 发现已有未提交修改与本次任务冲突。

### 3.3 始终禁止

- `git commit`、`git push`，以及创建、编辑、评论、审批、合并、关闭、重开等任何 PR 变更；
- 部署、灰度、发布或修改线上配置；
- 连接或写入任何数据库；
- 实际执行写数据 SQL、调用会改变外部状态的接口；
- 把密码、Token、Cookie、生产 DSN 或敏感生产数据发送给第三方；
- 用 `git reset --hard`、`git checkout --` 等命令覆盖你的修改；
- 未经确认删除本地文件或本地可恢复资源；
- 删除数据库表/数据或外部系统资源始终不得执行；即使你确认，也只能生成脚本、风险说明和人工操作步骤。

> 不提交 Git 不代表不用 Git。`git status`、`git diff` 和 `git log` 是核对本地修改的重要只读工具。

### 3.4 提示词约定与实际权限要分别落实

“不提交、不发布、不连接数据库”是你给 AI 的任务约定，不是输入后就自动启用的软件强制保护。Skill 也不能替代客户端权限和操作系统限制。使用客户端当前提供的受限工作区、网络权限和逐项审批；分析阶段选择只读能力（若有），实施阶段仅开放目标目录写入。不要为了省确认而启用跳过审批或无限制访问。权限名称以当前客户端为准。

“只读分析”在本文指不修改项目源文件、不改变外部业务状态。构建或 Go 工具命令仍可能写缓存、下载模块/工具链，某些情况下改变校验文件。`go list`、`go test`、`go vet`、`go build` 都不能仅凭名称视为零副作用。先读 `go.mod` / `go.work` 和测试配置，核对本机工具链、缓存与网络需求；依赖下载未获授权时采用离线设置，缺依赖就报告，不擅自下载。`-mod=readonly` 也不是全盘只读保证。执行后核对 `go.mod`、`go.sum`、`go.work`、`go.work.sum` 和其他工作区差异。

### 3.5 规则放哪里，换会话如何继续

按三个层次管理规则，不要求创建 `AGENTS.md` 或其他新规则文件：

| 层次 | 保存与引用方法 | 生效检查 |
|---|---|---|
| 个人长期规则 | 把模板 0 保存在自己的常用文本/本手册中，新会话粘贴；可自愿使用个人 Skill 保存通用流程 | AI 首轮复述不提交、不发布、不连接数据库等约定；插件安装不代表它记住了这些规则 |
| 项目固定规则 | 使用项目已有 README、开发文档、PRD/TRD、规格；新会话明确给路径及相关章节 | AI 先读取，列出来源、适用目录、版本和冲突；不得只说“遵守规范” |
| 单次任务要求 | 任务卡中写目标、文件范围、非目标、验收与本轮权限 | AI 复述后再分析；变更超出批准范围时询问 |

项目规则至少核对：技术栈和版本、目录职责、命名约定、公共接口/数据契约、禁止修改范围、生成文件处理、依赖新增/升级政策、验证命令与副作用。已有资料未覆盖的部分，先在对话确认；你明确授权后才更新指定的现有文档，不自动新建规则文件。

Codex 支持 `AGENTS.md` 指令文件机制；若项目本来有此类文件，应读取实际适用的全局、项目及子目录规则并说明来源。本教程不要求也不创建它；“不创建”不代表忽略已经存在的规则。具体发现顺序与覆盖关系按当前官方说明/客户端提示核对，不能假定一个插件就替代了指令文件或跨会话记忆。

每次新会话先复制这段，并填写实际路径：

```text
个人规则：不创建 AGENTS.md 等规则文件；不提交 Git、不变更 PR、不发布、不连接或写入数据库、不改变外部系统。
项目规则来源：【已有 README/开发文档/PRD/TRD 的真实路径及章节】。
本轮任务：【目标、范围、非目标、验收标准】；本轮只读，不修改文件、不安装依赖、不启动服务。
请先读取规则，复述：规则内容、来源、适用目录，以及冲突/缺失项。
不能读取的明确标为未读取；不要把示例或推测当成生效规则，也不要重复索要已经明确给出的授权。
```

如果 AI 没有列出实际文件来源，先要求补读；“已理解”不能证明已读取。换会话时重新引用这些路径和已确认决策，不依赖旧聊天自动延续。

### 3.6 确认规则与文档写入权限

默认两次批准：先确认采用的方案，再确认含文件范围、测试命令、风险和停止条件的实施计划。需求澄清可以有多次问答，这不等于重复请求同一权限。已有批准仍然有效，不让 AI 每一步重新问。

仅在以下条件全部满足时，可合并为一次批准：单仓库、局部且可逆、需求无歧义；不涉及公共契约、表结构、依赖、权限、安全或事务语义变化。AI 必须同时展示短方案、准确文件范围、非目标和验证计划；你回复“确认以上短方案及实施计划，允许修改列出的文件并运行列出的本地验证”后才实施。“小任务”不是按代码行数判断，条件不满足就用默认流程。

| 当前授权 | 可以做 | 不能据此做 |
|---|---|---|
| 只分析/设计/计划 | 对话展示草案、读取指定资料 | 保存计划、写测试、调试插桩、生成脚本文件 |
| 仅保存文档草案到明确路径 | 写入指定文档；OpenSpec 限批准的变更目录 | 写业务代码、测试、依赖或项目规则文件；执行文档中的命令 |
| 已批准方案和实施计划 | 修改列出的代码/测试，运行已审查副作用的相关本地验证 | 扩大需求、改范围外文件、执行本教程禁止动作 |
| 只做 Review/交接/报告 | 审查差异、整理已有证据及其时间与范围 | 顺手修复、格式化、为了凑报告重新执行测试 |

文档落盘可以单独授权，例如“仅将这份计划保存到【准确路径】，不授权执行计划或改代码”。如果本轮请求已明确指定准确路径并要求生成/更新该文档，这就构成相应文档写入授权，不再重复询问；文件系统沙箱可能仍需另行授予目录访问权限。Superpowers/OpenSpec 如要求自动保存到其他路径、创建指令文件或提交，必须按当前授权收窄；不能因此提前改文件。

## 4. 开始任务前的 5 分钟准备

### 4.0 第一次使用：从登录到成功读取仓库

前提：你能在终端使用 Git、项目要求的 Go/Node 等工具；本教程不是从零安装开发环境。第一次先用无敏感内容的本地练习，暂不连接公司的数据库或服务。

1. 尚未安装 Codex 时，从 [Codex 官方入口](https://developers.openai.com/codex/)进入当前平台下载/安装说明；只使用官方渠道。已安装就跳过，不要重复安装。
2. 启动客户端，按界面完成自己的账号登录；不要把登录码、API Key 或 Cookie 发到对话里。成功标志是可以创建任务、发送消息并收到回答；若报账号/权限错误，先解决登录，不把它误判为代码问题。
3. 桌面端从项目/文件夹入口选择**具体仓库根目录**；VS Code 用“打开文件夹”打开同一根目录；CLI 在该目录执行 `codex`。入口名称随版本变化，以当前 UI 和帮助为准。
4. 首轮只做分析，使用受限权限；只开放所需目录，网络和额外目录按需审批。不选绕过权限检查。若插件需要自动保存/commit，以你的任务边界为准。
5. 发送下面的话，核对返回的路径、现有修改、实际规则来源是否正确。这个阶段不需要 OpenSpec，也不用先装齐所有插件。

```text
我第一次在此项目使用 Codex。当前只读，不改文件、不安装依赖、不启动服务。
请确认当前目录；如果是 Git 仓库，报告 git status 的已有修改；如果不是，明确说明。
只读取已有 README、go.mod/go.work（若存在）和适用规则，列出实际路径。
复述生效规则和来源，不创建 AGENTS.md，不执行构建/测试或联网命令。
```

成功标志：AI 引用的根目录与你选择的一致，没有混入邻近仓库；规则来源可打开；原有修改未变；没有偷偷启动服务或下载依赖。看不见仓库时先纠正目录/访问权限，不继续实现。接着做第 4.5 节练习，再开始正式项目。

### 4.1 选择正确入口

| 任务状态 | 从哪里开始 |
|---|---|
| 只有 PRD、设计稿、文档，需要先理解 | ChatGPT Work |
| 已有明确需求，要分析或改真实代码 | 对应项目的 Codex 任务 |
| 正在 VS Code 阅读具体代码 | VS Code Codex 面板 |
| 希望在终端快速检查、运行命令 | Codex CLI |
| 涉及多个仓库 | 每个仓库单独项目/任务，主任务保存整体依赖关系 |

### 4.2 准备四类信息

```text
目标：最终要改变什么行为。
上下文：PRD、设计稿、接口、代码目录、日志和截图在哪里。
约束与非目标：哪些不能变、哪些本次不做。
完成标准：怎样客观证明完成。
```

### 4.3 检查本地状态

在项目根目录执行或让 Codex 执行：

先读取 `go.mod` / `go.work` 的版本要求；下面的 Go 查询使用本地工具链，版本不满足时会报错，不能顺手下载。`git` 命令仅适用于 Git 仓库。

> 命令示例中的 `/path/to/...`、`path/to/...` 等内容是占位符，执行前必须替换为当前项目的真实路径。

```bash
pwd
git status --short --branch
git diff --stat
git diff --cached --stat
git ls-files --others --exclude-standard
GOTOOLCHAIN=local go version
GOTOOLCHAIN=local go env GOMOD GOWORK GOPATH GOPROXY GOPRIVATE
```

目的：确认仓库、识别已有修改和未跟踪文件、核对 Go 模块及私有依赖环境，避免误改或覆盖。

### 4.4 检查插件，但不要为每个任务重复安装

Superpowers：

- 桌面端在插件列表搜索 `Superpowers`；
- CLI 打开插件界面搜索，或使用本机支持的插件列表命令；
- 在新对话说“使用 Superpowers brainstorming 梳理需求”，观察是否按一次一个问题工作。

OpenSpec：

## 5. 标准研发流程：八个阶段

### 阶段 1：建立任务卡

先在对话中提供：

```text
任务类型：【PRD梳理 / 新功能 / Bug / 重构 / 性能优化】
目标：【一句话结果】
依据：【文件、链接、代码目录、日志】
范围：【允许涉及的仓库、模块】
非目标：【明确本次不做什么】
硬约束：【接口、表、兼容性、安全规则】
完成标准：【可验证条件】

本轮只分析，不修改文件。区分事实、推测、冲突、缺失和建议；一次只问我一个关键问题。
```

合格输出应包含：资料清单、已确认事实、冲突/缺失、影响范围和第一个关键问题。

### 阶段 2：只读侦察真实项目

切到 Codex，对它说：

```text
请先只读检查当前仓库：
1. 确认仓库状态和已有用户修改；
2. 找到需求涉及的入口、调用链、数据模型、接口和测试；
3. 列出事实证据，附文件路径和必要行号；
4. 判断 PRD 与现有实现是否冲突；
5. 不修改文件，不安装依赖，不启动服务。
```

AI 应先阅读本项目，而不是套用通用架构。若涉及多仓库，必须输出仓库职责和依赖方向。

### 阶段 3：一次确认一个关键问题

要求 AI 按影响从高到低提问：

1. 会改变用户行为或数据结果的问题；
2. 会改变公共接口、表结构或兼容性的问题；
3. 会改变实现范围和工期的问题；
4. 纯技术细节，能遵循现有模式的通常无需问。

每次回答后，让 AI 复述新结论并更新“已确认/未确认”清单。不要一次收到几十个混杂问题。

### 阶段 4：方案设计与确认

使用 Superpowers：

```text
@Superpowers 使用 brainstorming 基于已确认需求和真实代码提出 2-3 个方案。

每个方案说明：
- 数据和调用流程；
- 修改范围；
- 兼容性；
- 异常与并发处理；
- 测试方式；
- 风险和取舍。

给出推荐方案和依据。方案确认前不要修改代码。
```

确认时不要只回复“可以”，建议明确：

```text
确认采用方案 B，并补充：
1. 保持现有 RPC 响应字段兼容；
2. 不新增数据表；
3. 本次不实现后台配置页面；
4. 按方案进入实施计划，仍不要修改代码。
```

### 阶段 5：实施计划

复杂任务使用当前客户端的计划入口（若提供 `/plan`），或明确指定 `writing-plans`。草案默认只输出在对话中：

```text
使用 Superpowers writing-plans，把确认方案拆成可独立验证的任务。

计划必须包含：
- 每步涉及的具体文件；
- 输入、输出和依赖；
- 测试先行步骤；
- 每步验证命令；
- 多仓库执行顺序；
- 失败时的停止条件。

禁止包含 commit、push、任何 PR 变更、部署、发布、连接或写入数据库，以及外部系统写入。只在对话中输出计划，不保存文件、不创建 AGENTS.md；输出后等待我确认。
```

检查计划是否夹带未确认需求、无关重构或 Git 提交步骤。Superpowers 原始流程可能建议频繁 commit，你的边界优先，必须删除这些步骤。

### 阶段 6：实施

你确认计划后发送：

```text
计划确认，开始实施。

要求：
- 严格按计划和现有项目规范修改；
- 保留已有用户修改；
- 使用测试驱动覆盖新增或修复行为；
- 遇到超出范围、需求冲突或公共契约变化时立即停止询问；
- 不执行 commit、push、任何 PR 变更、部署、发布，不连接或写入数据库，也不改变外部系统；
- 完成前持续更新任务进度。
```

小任务可以用短方案与短计划，只有满足第 3.6 节全部条件且你明确合并批准，才可以一次确认后实施；不能只凭“任务小”跳过计划。

### 阶段 7：验证

要求 AI 根据改动选择验证层级：

```text
请重新执行与本次改动直接相关的验证：
1. 格式化和静态检查；
2. 精确单元测试；
3. 相关包测试；
4. 必要时才运行更大范围测试；
5. 核对验收标准和异常流程。

列出实际命令、退出码、关键结果、未执行项和原因。不得用“应该通过”替代结果。
```

Go 项目常见顺序如下。执行前必须先检查测试代码、配置和环境变量；如果可能连接数据库、队列、外部 API、测试/生产环境或真实凭据，则不执行这些命令，改用 mock/单元测试或只提供人工步骤：

```bash
gofmt -w path/to/changed.go
go vet ./path/to/changed/package/...
go test ./path/to/changed/package/... -count=1
go test ./related/module/... -count=1
```

`gofmt -w` 会修改文件，必须限定到本次文件。`go mod tidy`、`go generate` 也会修改文件，未经需要不要执行。

### 阶段 8：本地 Review 与交付

在桌面端或 CLI 使用 `/review`，或者输入：

这里的“Review”是检查当前本地差异：可使用客户端 `/review` 命令、Superpowers 的 `requesting-code-review` Skill，或直接发送下面的自然语言提示。三种入口目标相同，不代表提交 PR。

严重度统一口径：

- **P0**：会造成数据丢失、安全事故、核心服务不可用等灾难性影响；立即停止交付，必须先修复。
- **P1**：会导致核心功能错误、明显回归或公共契约破坏；本次本地交付前必须修复。
- **P2**：非阻断问题、可维护性问题或测试缺口；允许记录后续处理，但必须说明风险和建议。

```text
Review 当前未提交修改。

重点检查：
- 是否满足已确认需求和验收标准；
- 是否存在 Bug、回归、并发、事务和兼容风险；
- 是否遗漏异常路径或测试；
- 是否混入无关修改；
- 是否误改已有用户文件。

先按 P0/P1/P2 列出问题并引用文件位置；没有问题时明确说明剩余风险。不要修改代码。
```

最终报告必须包含：

- 实际修改文件；
- 行为变化；
- 实际验证命令与结果；
- 未验证内容及原因；
- 剩余风险；
- `git status --short` 和未跟踪文件情况；
- 明确说明未 commit、未 push、未进行任何 PR 变更、未部署、未发布、未连接或写入数据库、未改变外部系统。

## 6. 各类场景应该怎么操作

### 6.1 PRD 梳理与生产级需求

**推荐入口**：先用 ChatGPT Work；需要核对真实实现时切到 Codex。

操作流程：

1. 给 Work 提供原始 PRD、正式 UI、接口文档和已有约束。
2. 明确资料优先级，例如“正式 PRD > 正式 UI > 接口文档；演示原型仅参考”。
3. 要求区分事实、推测、冲突、缺失、建议。
4. 一次确认一个会改变业务结果的问题。
5. 输出 AI 执行版 PRD：范围、角色、流程、规则、状态、异常、权限、数据、接口、验收、非目标。
6. 切到代码仓库的 Codex，只读核对需求与真实实现。
7. 让 Codex 列出无法由代码证明的业务假设，再返回 Work/产品确认。

合格标准：

- 每条关键规则可判断“通过/不通过”；
- 正常、异常、空状态、并发和权限路径明确；
- 名词、状态和值域唯一；
- 资料冲突有明确裁决；
- 没有把技术建议写成已确认产品规则；
- 非目标清楚，避免 AI 顺手扩展。

### 6.2 新功能

默认使用：

```text
brainstorming -> writing-plans -> test-driven-development
-> verification-before-completion -> review
```

关键要求：先找现有相似功能；确认接口兼容、数据所有者、事务和幂等；方案和计划均获批准后才编辑，包括先写失败测试；最终从用户可见行为反向核对验收标准。

### 6.3 Bug 修复

默认使用：

```text
systematic-debugging -> test-driven-development -> verification-before-completion
```

执行顺序：

1. 用已有日志、测试或经副作用检查的本地操作复现，不新增文件或插桩；
2. 从日志、调用链、状态和数据找到根因证据；
3. 在对话中展示最小修复方案、涉及文件和回归测试计划，按第 3.6 节取得方案与计划批准；
4. 批准后写一个修复前会失败的回归测试，实际确认失败原因符合预期；
5. 做最小修复，重新运行原复现和相关回归。

如果复现必须新增测试、临时脚本或插桩，也先申请准确文件范围的诊断实验授权；这不等于已批准修复方案，更不允许访问数据库/外部系统。

禁止：看到报错就改、一次混入多个猜测、吞掉错误、盲目重试、扩大重构范围。

### 6.4 重构

先定义必须保持不变的可观察行为：对外接口和错误码、RPC/HTTP 字段、数据读写结果、事务和并发语义、必要日志/指标/事件契约。

如果测试不足，先在方案中列出特征测试，方案与计划获批后再写。每一步应保持可编译、可测试；不要把新功能混进重构。

### 6.5 性能优化

性能结论至少包含：

```text
基线环境 + 数据规模 + 负载模型 + 当前指标 + 目标指标 + 测量工具
```

流程：固定条件建立基线；用 profile、trace、用户提供的 SQL 执行计划或指标证明瓶颈；如需 `EXPLAIN`，只生成语句供人工执行并分析用户提供的结果，AI 不连接数据库；一次验证一个假设；确认后最小优化；相同条件复测平均值、P95/P99、错误率和资源消耗；最后做正确性回归。

没有前后对比数据时，只能说“实施了优化尝试”，不能说“性能已提升”。

## 7. 单仓库与多仓库

### 7.1 单仓库

一个任务绑定一个项目根目录。开始时确认：

```bash
pwd
git rev-parse --show-toplevel
git status --short --branch
```

不要从父目录启动后让 AI 搜索全部工作区，这会增加误改邻近仓库的风险。

### 7.2 多仓库

先建立依赖表：

| 仓库 | 职责 | 本次改动 | 对外契约 | 验证方式 |
|---|---|---|---|---|
| 服务 A | 数据/业务规则所有者 | 表模型、RPC | RPC v1 兼容 | 单测、集成测试 |
| 服务 B | API 聚合 | 字段透传、HTTP | HTTP 响应兼容 | Handler 测试 |
| 客户端 C | 消费者 | 展示新字段 | 兼容字段为空 | UI/契约测试 |

推荐顺序：

```text
契约确认 -> 提供者实现 -> 提供者验证 -> 消费者适配 -> 跨仓联调说明
```

每个仓库分别记录根目录、分支、已有修改、Go 版本、启动/测试命令。不要让多个代理同时修改同一个共享文件。

多仓任务提示：

```text
这是多仓库变更。先不要修改代码。

请输出：
1. 每个仓库的职责和数据所有权；
2. 调用方向和公共契约；
3. 向前/向后兼容策略；
4. 推荐修改顺序；
5. 每个仓库独立验证方式；
6. 跨仓联调仍需要人工完成的事项。

如果某个仓库不可访问，不要猜测其实现。
```

## 8. OpenSpec 的具体使用方法

### 8.1 什么时候不要使用

- 只改一个判断或文案；
- 根因明确的小 Bug；
- 一次性分析，不会形成代码变更；
- 需求还没确认；
- 引入规格文件的维护成本高于任务价值。

此时直接用 Superpowers 的短设计和计划更轻。

### 8.2 第一次在项目使用

进入明确的项目根目录：

```bash
cd /path/to/project
openspec --version
openspec init --tools codex
```

注意：

- `init` 会创建项目内文件，先看 `git status`，预览并确认生成范围；不能创建 `AGENTS.md` 等规则文件，无法避免时暂不初始化；
- 不要在包含多个仓库的公共父目录初始化；
- 初始化后重开 Codex 任务，确保 Skills 被读取；
- 在 Codex 输入 `$` 或查看 Skills，确认实际可用名称。

OpenSpec 1.14.1 为 Codex 生成的常见 Skills 包括：

- `$openspec-propose`
- `$openspec-apply-change`
- `$openspec-verify-change`
- `$openspec-archive-change`
- `$openspec-explore`

桌面端可能要求从 Skills 侧栏选择名称，而不是直接输入 `$`。以 `openspec init` 的提示和当前客户端 UI 为准。

### 8.3 复杂功能的推荐组合

1. **先澄清**：用 Superpowers `brainstorming` 一次确认一个问题。
2. **创建规格**：先在对话展示提案草案；你明确授权“仅保存到 `openspec/changes/实际变更名/`”后，才使用 `openspec-propose` 写已确认内容。不授权业务代码、测试或规则文件。
3. **检查规格**：规格已获准保存后，可运行当前版本支持的列表/规格校验命令；先确认不会安装依赖、联网或改变外部状态。

```bash
openspec list
openspec status
openspec validate order-cancel-reason
openspec show order-cancel-reason
```

其中 `order-cancel-reason` 是示例变更名，执行时替换为实际的英文短横线名称；不要输入尖括号。

4. **计划**：用 `writing-plans`，删除所有 commit、push、任何 PR 变更和发布步骤，等你确认。
5. **实施**：选择 `openspec-apply-change`，同时要求测试驱动和停止条件。
6. **验证**：选择 `openspec-verify-change`，把每条规格映射到代码与测试证据。
7. **归档**：`openspec-archive-change` 会修改 OpenSpec 文件。你不需要强制归档；只有明确需要整理本地规格时才执行，且仍不得 commit。

### 8.4 默认策略

```text
Superpowers 默认启用；OpenSpec 按复杂度启用。
```

比 OpenSpec 更合适的轻量方案通常是：已确认 PRD + Codex `/plan` + 验收清单。只有“长期保存和追踪规格”确实创造价值时才引入 OpenSpec。

## 10. 桌面端、VS Code 和 CLI 怎么选

### 10.1 Codex 桌面端

最适合完整任务、长流程、多文件修改、文档与浏览器协作。

1. 为仓库建立独立项目或从正确目录新建任务；
2. 检查页面显示的工作目录；
3. 用 `@` 引用文件、插件或应用；
4. 复杂任务先 `/plan`；
5. 实施结束后打开 diff 或使用 `/review`；
6. 保留当前任务用于同一问题的后续修正。

### 10.2 VS Code

最适合边读代码边提问、解释选中逻辑、小范围修改。

1. VS Code 只打开当前仓库根目录；
2. 在 Codex 面板引用当前文件或选中代码；
3. 明确关联入口和期望行为，不只发一段孤立代码；
4. 大范围任务交给桌面端项目或独立任务；
5. 修改后仍回到 Git diff 和测试验证。

### 10.3 Codex CLI

最适合习惯终端、需要快速执行命令、远程或纯代码环境。

```bash
cd /path/to/repository
codex
```

常用动作：

- `/plan`：复杂任务先规划；
- `/review`：Review 差异、提交或相对分支；
- `/status`：查看当前会话状态；
- `/resume`：恢复已保存会话；
- `/fork`：从当前上下文分叉一个真正不同的方向；
- `/compact`：压缩过长上下文；
- `/plugins`：插件界面（若当前版本提供）。

客户端命令会随版本变化，输入 `/` 查看当前可用命令，不要盲目照抄不存在的命令。

### 10.4 `@`、`/`、`$` 的区别

| 符号 | 用途 | 示例 |
|---|---|---|
| `@` | 引用文件、应用或插件 | `@Superpowers`、`@api.md` |
| `/` | 客户端命令 | `/plan`、`/review`、`/status` |
| `$` | 显式选择 Skill（支持时） | `$openspec-propose` |

如果补全列表没有某个名称，不要硬输。改用自然语言“使用 Superpowers 的 systematic-debugging”，或从当前 Skills/插件列表选择。

## 11. 模型与推理强度

不需要频繁换模型。优先使用客户端当前推荐的通用编码模型，再按任务调整推理强度。

| 任务 | 推荐强度 |
|---|---|
| 查文件、解释代码、小范围明确修改 | Low/Medium |
| PRD 与代码核对、一般新功能、常规 Bug | Medium/High |
| 复杂根因、跨服务设计、并发/事务问题 | High/Extra High |
| 简单格式转换、机械整理 | Low |

提高强度不能弥补缺少上下文。对复杂任务，先提供正确文件、日志、验收标准，再考虑提高推理强度。

## 12. 会话、项目、Fork 和 Worktree

### 12.1 继续当前会话

- 仍在解决同一个需求或 Bug；
- 新问题依赖当前已确认结论；
- 正在对刚生成的方案、代码或 Review 反馈迭代。

### 12.2 新建会话

- 目标已经改变；
- 切换到另一个独立功能或 Bug；
- 旧会话包含大量无关历史，容易污染判断；
- 需要在另一个仓库执行独立工作。

### 12.3 Fork 会话

同一事实基础上，需要比较两个互斥方案时使用。Fork 后两个会话不会自动同步新结论，最终要明确采用哪个方向。

### 12.4 Worktree

只有在需要隔离不同任务或并行修改时使用。Worktree 是另一个检出目录，不是备份，也不会自动保存未提交改动。

你的特殊规则：

- 创建 Worktree 前必须确认；
- 不允许 Superpowers 自动 commit；
- 不并行修改相同文件；
- 完成后只交付本地差异和验证结果，不合并、不提交。

### 12.5 长会话管理

- 一个会话只服务一个清晰结果；
- 阶段结束时让 AI 输出“已确认事实、未决问题、修改和验证”；
- 上下文过长时使用 `/compact`，压缩后复核关键约束；
- 新会话首条消息附上最终 PRD、计划、当前 Git 状态以及第 3.5 节的规则路径；要求复述生效规则与来源，不复制全部闲聊历史。

## 13. Go 项目的验证方法

### 13.1 先确认模块边界

先阅读模块文件再执行命令。下面禁用自动工具链/模块下载；这仍可能写本地缓存，不等于只读沙箱。缺少本地版本/依赖时停止并报告，下载需单独授权，不修改依赖版本来绕过。

```bash
GOTOOLCHAIN=local go version
GOTOOLCHAIN=local go env GOMOD GOWORK GOPATH GOPROXY GOPRIVATE CGO_ENABLED
GOTOOLCHAIN=local GOPROXY=off GOSUMDB=off go list -mod=readonly -m
GOTOOLCHAIN=local GOPROXY=off GOSUMDB=off go list -mod=readonly ./path/to/package/...
```

- `go.mod` 锁定依赖版本；清缓存不会自动升级依赖；
- `go.work` 可能让项目使用本地模块而不是缓存版本；
- 私有模块需要正确的 `GOPRIVATE`、网络和凭据；
- CGO、构建标签和目标 OS 可能导致本机测试与生产构建不同。

### 13.2 分层验证

运行任何测试前，先只读检查测试代码、配置和环境变量，确认不会连接数据库、队列、外部 API、测试/生产环境，也不会读取真实凭据或改变外部状态。无法排除副作用时停止执行，改用 mock/单元测试，或只提供人工验证步骤。

```bash
# 精确测试
go test ./internal/path -run '^TestSpecificBehavior$' -count=1

# 相关包
go test ./internal/path/... -count=1

# 静态检查
go vet ./internal/path/...

# 并发风险（项目支持时）
go test -race ./internal/path/... -count=1

# 全量测试（成本和环境允许时）
go test ./... -count=1
```

以上命令也受第 3.4 节的下载/缓存约束；未授权下载时同样设置 `GOTOOLCHAIN=local GOPROXY=off GOSUMDB=off` 并视项目支持使用 `-mod=readonly`，不要忽略自定义构建脚本的联网行为。执行后复核模块/校验文件和 Git 差异。

记录每条命令的范围。某个包测试通过，不代表数据库集成、跨服务联调和生产环境都通过。`-race` 只检查实际执行路径中的内存数据竞争；通过只能说“受测路径未发现数据竞争”，不能证明没有所有并发问题、事务隔离错误或死锁。

### 13.3 Go 修改常见风险

- `go mod tidy` 会修改 `go.mod/go.sum`；
- `go generate` 会覆盖生成文件；
- `gofmt -w` 会写文件，避免格式化整个仓库；
- 指针、零值、JSON/Form 标签和兼容性需要分别验证；
- goroutine、channel、锁和共享 map 需要考虑竞态与退出；
- `context` 的超时和取消必须沿调用链传递；
- 事务函数内部不要混入不可回滚的外部副作用。

## 14. MySQL 与 SQL 的安全方法

本教程默认只生成 SQL，不执行。

设计或 Review 时至少检查：

- 表和字段的所有者；
- 主键、唯一性、普通索引和查询条件；
- `NULL`、默认值、金额精度、时区和字符集；
- 逻辑删除与唯一索引的组合；
- 事务边界、锁顺序、死锁与幂等；
- 迁移的向前/向后兼容；
- 多仓库客户端升级窗口；
- 大表 DDL 和数据回填风险。

连接概念：

- `localhost` 在某些 MySQL 客户端中可能走 Unix Socket；
- `127.0.0.1` 明确走 TCP；
- 不要把真实 DSN、密码和生产地址写进提示词或文档；
- 使用占位符和合成数据。

生成 SQL 时要求：

```text
只生成 SQL 文件和预检/回滚说明，不连接或写入任何数据库。
所有数据假设、影响行数估算、幂等条件和风险必须列出。
涉及 DROP、TRUNCATE、DELETE、UPDATE 或大表 DDL 时单独标红，不得执行。
```

## 15. 完整主案例：跨仓库新增订单取消原因

这是示范流程，不对应真实项目。

### 15.1 背景

- `order-core`：Go 服务，拥有订单表和 RPC；
- `order-api`：Go 服务，对外提供 HTTP 订单详情；
- 需求：订单取消后，详情页返回取消原因；
- MySQL 只允许生成 DDL，不执行；
- 旧客户端必须继续工作。

### 15.2 在 Work 梳理 PRD

```text
梳理“订单取消原因展示”需求。

请一次只问一个问题，最终明确：
- 哪些取消状态需要原因；
- 原因来源、值域和为空行为；
- 用户可见文案；
- 历史订单处理；
- 权限与隐私；
- HTTP/RPC 兼容性；
- 验收标准和非目标。

只整理需求，不做技术实现假设。
```

### 15.3 在 Codex 只读调查两个仓库

```text
依据已确认 PRD，只读分析 order-core 和 order-api。

输出仓库职责、取消流程调用链、订单模型、RPC/HTTP 契约、现有测试和兼容风险。
先检查两个仓库的 git status，保留已有修改。不要修改文件。
```

### 15.4 逐项确认

依次确认：原因存储为枚举码还是文本；历史订单为空时的展示；RPC 新字段是否可选；需要数据库字段还是已有权威来源。

一个兼容设计示例：

- `order-core` 是取消原因的数据所有者；
- RPC 响应新增可选字段，旧消费者忽略；
- `order-api` 只透传和做展示映射，不重复推导规则；
- 历史订单返回空值，客户端不展示；
- 数据库 DDL 单独生成，不执行；
- 提供者先完成和验证，再适配消费者。

### 15.5 计划与实施

```text
方案确认。使用 writing-plans 按以下顺序规划：
1. order-core 回归/新增测试；
2. 数据模型和取消写入逻辑；
3. RPC 契约与兼容测试；
4. order-api 字段映射与 Handler 测试；
5. 跨仓契约核对；
6. SQL 文件及人工执行说明。

只在对话输出计划，不保存文件、不写测试或业务代码，等待我确认实施计划。禁止 commit、push、任何 PR 变更、部署、发布、连接或写入数据库，以及外部系统写入步骤。
```

确认后再实施。若无法同时打开两个仓库，应分别建立任务，并把已确认契约作为两个任务的共同输入。

### 15.6 验收

| 验收条件 | 证据 |
|---|---|
| 取消订单返回原因 | `order-core` 精确单测 |
| 非取消订单不返回原因 | 边界测试 |
| 历史空值兼容 | RPC/HTTP 契约测试 |
| 旧字段无变化 | 响应快照或回归测试 |
| 受测路径未发现内存数据竞争 | 指定并发测试与可运行时的 `-race`；记录场景、命令和范围，不推广到全部调度 |
| 数据库隔离、锁顺序、死锁与回滚符合约定 | 本地仅静态审查与 mock；真实数据库验证由人工完成，当前标记未验证 |
| 跨服务真实联调符合契约 | 本地契约测试不替代真实联调；由人工验收并回填证据 |
| SQL 未执行 | 交付报告明确声明 |

最后 `/review` 两个仓库的未提交差异，分别报告测试结果和剩余联调项。

## 16. 三个简短案例

### 16.1 Bug：偶发重复扣减

只读检查已有并发证据、幂等键、事务隔离、锁顺序和重试路径；先确认修复方案与测试计划，再写能失败的并发测试并最小修复。模拟测试不能证明真实数据库事务行为，数据库复现留给人工。不要先加锁或重试碰碰运气。

### 16.2 重构：拆分 800 行 Service

先列出公共方法、调用者和行为契约；用现有测试或特征测试锁定行为；按职责小步拆分；每一步运行相关测试。禁止同时改接口、业务规则和数据库。

### 16.3 性能：订单列表 P99 过高

固定数据量、并发和机器；记录 P50/P95/P99、错误率、CPU、内存；用 Trace、用户提供的执行计划等证据定位慢 SQL、N+1 或外部调用；如需 `EXPLAIN`，只生成语句供人工执行并分析返回结果；一次验证一个假设；同条件复测，正确性回归后再下结论。

## 17. 失败时如何继续，而不是让 AI 乱改

| 问题 | 正确处理 |
|---|---|
| 测试失败 | 区分代码失败、环境失败、旧有失败；保留完整命令和首个根因 |
| 依赖下载失败 | 检查网络、GOPROXY/GOPRIVATE 和权限；不要改业务代码绕过 |
| 端口占用 | 找到占用进程和归属；确认后再停止，不盲目 kill |
| 用户提供 MySQL 连接失败日志 | 从日志区分 Socket/TCP、服务状态、账号权限和库是否存在；AI 不实际连接 |
| 测试偶发失败 | 重复运行并记录频率、随机种子和并发条件；不要直接重跑到绿 |
| 上下文中断 | 输出当前事实、计划进度、修改、验证和下一步，再开新任务 |
| 发现需求冲突 | 停止实现，回到一次一个问题的确认流程 |
| 用户已有修改 | 不覆盖、不回滚；分清本次差异，必要时请求你决定 |

通用停止提示词：

```text
停止继续猜测修改。请使用 systematic-debugging：
1. 保留当前失败证据；
2. 区分环境问题、既有问题和本次回归；
3. 给出最小验证实验；
4. 在根因确认前不要修改业务代码。
```

## 18. 如何判断交付是否合格

只有同时满足以下条件，才可以认为本地实现完成：

- 需求、方案和实施计划经过你确认（合并批准仅限第 3.6 节条件）；
- 修改范围与计划一致；
- 本地范围内每条验收标准都有对应证据；需真实环境的条目明确标记未验证和人工责任人，不能算作已完成验收；
- 实际执行了相关格式化、检查和测试；
- Review 没有未处理的 P0/P1 问题；
- 未验证项和剩余风险已明确；
- 已有用户修改未被覆盖；
- 没有 commit、push、任何 PR 变更、部署、发布、数据库连接或写入，也没有改变外部系统；
- 本地进程、临时文件和测试资源得到说明或清理。

不要接受：“理论上可行”“应该能通过”“代码看起来没问题”“已经优化但没有前后数据”“完全符合 PRD 但没有逐条映射”。

## 19. 推荐的日常使用习惯

1. 每个独立结果一个会话，不把整个项目堆在一个会话。
2. 第一条消息始终写目标、上下文、约束/非目标、完成标准。
3. 正式项目默认先分析、确认方案，再确认实施计划和文件范围，才授权修改。
4. 新功能和 Bug 默认使用 Superpowers；复杂跨仓再加 OpenSpec。
5. 让 Codex 先读项目现有模式，不让它凭空设计。
6. 验证必须给实际命令、退出状态和范围。
7. 最后使用 `/review`，不要把“测试通过”等同于“没有风险”。
8. 重复出现的流程可以做成 Skill；不要为了工具而工具。
9. 永远不粘贴真实密钥、Token、Cookie 或生产 DSN。
10. 把最终决定保存在 PRD、计划或 OpenSpec 中，不依赖聊天记忆。

## 21. 常用术语速查

| 术语 | 简单理解 | 使用时注意 |
|---|---|---|
| PRD | 产品需求说明：用户要什么、规则是什么、怎样验收 | 技术猜测不等于产品已确认 |
| TRD | 技术方案说明：系统怎样实现需求、接口/数据/异常怎样处理 | 应基于实际工程与已确认 PRD |
| 契约 | 调用双方共同遵守的字段、值域、错误码和行为约定 | 字段没变不代表语义一定兼容 |
| 幂等 | 相同业务请求重复执行仍只产生约定的一次业务效果 | 重试不等于幂等，需要业务键和边界 |
| mock | 用可控替身模拟依赖的响应、错误与调用 | mock 通过不能证明真实服务一致 |
| 特征测试 | 先记录已有实现的可观察行为，供重构时比较 | 它可能记录既有 Bug，不自动代表正确需求 |
| P95 / P99 | 一组样本中约 95% / 99% 的耗时不超过该值 | 不是平均耗时；算法、样本量、负载和环境需一致 |
| diff / Review | 查看改动差异 / 审查行为、风险和遗漏 | Review 不代表创建或提交 PR |
| 三个阶段 | 分析、方案与计划、实施验证交接 | 允许多次问答，默认方案和计划分别批准 |
